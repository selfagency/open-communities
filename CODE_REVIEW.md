---

## Executive Summary

Open Communities is a SvelteKit 5 + PocketBase directory app for Jewish congregations. The codebase is generally well-organized, uses modern Svelte 5 runes syntax, has typed PocketBase responses, includes ~140 test files (mostly component tests), and has reasonable separation between client/server. The maintainer clearly cares about the craft.

However, **the review surfaced multiple CRITICAL security defects that block merge to production in the current state**. The most severe are:

1. **Captcha bypass** — `validateCaptcha()` returns a truthy `fail()` object on validation failure; callers do `if (captchaValid)`, so invalid captcha still creates records and sends emails. Bypasses the only anti-bot control on signup / add / contact / edit.
2. **IDOR in `/edit` submit action** — non-admin users can edit any congregation, not just their own, because the action only checks `client.id` exists, not that `client.congregation === data.id`. The `delete` action correctly checks ownership; `submit` does not.
3. **IDOR in `/user/lang` POST endpoint** — any authenticated user can change any other user's `lang` field; the `user` parameter is taken from the request body without comparing it to the authenticated client.
4. **PocketBase filter injection** — multiple `getFirstListItem(\`field="${userInput}"\`)` calls interpolate user-controlled values directly into PocketBase filter strings. The repo's own `pb.filter(expr, params)` helper is never used.
5. **Hardcoded production-looking secrets in CI** — `CAP_API_KEY`, `PB_TEST_PASSWORD`, `ADMIN_EMAIL` are checked into `.github/workflows/*.yml` in plaintext.
6. **Insecure auth cookies** — `httpOnly: false` and `secure: !dev` is commented out; combined with `script-src 'unsafe-eval' 'unsafe-inline'` in the CSP, any XSS exfiltrates auth tokens.
7. **SMTP transport disables TLS verification** — `tls: { rejectUnauthorized: false }` and `secure: false` are hardcoded.
8. **Email HTML injection** — `marked.parseInline(message)` output is interpolated into the email HTML template via `String.replace` without escaping; user input flows directly into HTML email bodies.
9. **Module-level PocketBase singleton mutated per-request** — `event.locals.api.beforeSend = …` mutates a shared singleton, so concurrent requests overwrite each other's client IP header.
10. **`authRefresh()` called on every request** — every authenticated page load triggers a PocketBase auth refresh, killing performance under any load.

Beyond these, there are dozens of HIGH/MEDIUM issues across type safety (many `any` types, unsafe casts), performance (N+1 patterns, transporter recreation per email), and architecture (duplicate API modules in `lib/api.ts` and `lib/server/api.ts`). Automated checks: typecheck passes after paraglide generation, but **lint fails** (ESLint config broken for CSS files, prettier fails on 6 files, 22 lint errors mostly for unresolved navigation), **unit tests do not run** in this environment due to a `@testing-library/svelte` ↔ Svelte 5 internal compiler incompatibility (`The $ name is reserved`), and one entire test file (`src/lib/server/mail.test.ts`) is `describe.skip`'d.

**Final recommendation: BLOCK UNTIL FIXED.** The CRITICAL items must be addressed before any further deployment. The HIGH items should be addressed in the same PR or a fast-follow. Section "Remediation Plan" below gives the ordered fix sequence.

### Category: Security Vulnerabilities

#### S-1. Captcha validation bypassed because `fail()` is truthy

- **Severity:** CRITICAL
- **File(s):** `src/lib/server/utils.ts:11-52`, `src/routes/add/+page.server.ts:90-92`, `src/routes/contact/+page.server.ts:68-93`
- **Description:** `validateCaptcha()` returns `fail(400, { form })` (an object) when the captcha is missing or fails verification. The caller in `add/+page.server.ts` does:
  ```ts
  const captchaValid = await validateCaptcha(form);
  if (captchaValid) { /* create records */ }
  ```
  A `fail()` object is truthy, so the `if` branch is taken even when captcha validation failed. The `contact/+page.server.ts` caller doesn't even check the return value — it just `await`s and proceeds to send the email regardless.
- **Why it matters:** The only anti-bot control on signup, congregation submission, contact form, and edit form is effectively a no-op. Attackers can submit unlimited fake congregations, spam the admin inbox, and burn PocketBase quota. Captcha cost is real (Cap API calls), but the verification is bypassed.
- **Affected code path:** Any user (authenticated or not) → `POST /add`, `POST /contact`, `POST /edit` → `validateCaptcha()` returns `fail(400)` → caller treats as success → records created / emails sent.
- **Root cause:** Confusion about `sveltekit-superforms`'s `fail()` semantics. `fail()` is meant to be *returned from an action*, not used as a generic "validation failed" signal inside a helper.
- **Recommended fix:** Make `validateCaptcha` return a strict boolean, and throw on misconfiguration:
  ```ts
  export async function validateCaptcha(form: SuperValidated<Record<string, unknown>>): Promise<boolean> {
    if (!pubEnv.PUBLIC_CAPTCHA_SITE_KEY || !env.CAPTCHA_SITE_SECRET) {
      throw new Error('Captcha validation is not configured');
    }
    if (!form.data.captcha) {
      setError(form, 'captcha', m.invalidCaptcha());
      return false;
    }
    const response = await fetch(...);
    const result = await response.json();
    if (!result?.success) {
      setError(form, 'captcha', m.invalidCaptcha());
      return false;
    }
    return true;
  }
  ```
  Then update callers:
  ```ts
  const captchaValid = await validateCaptcha(form);
  if (!captchaValid) {
    return fail(400, { form });
  }
  // proceed
  ```
- **Verification:** Unit test `validateCaptcha` with (a) missing captcha, (b) invalid captcha, (c) valid captcha, asserting `false`/`false`/`true`. E2E test that submitting the form with a deliberately wrong captcha token does NOT create a record.

#### S-2. IDOR in `/edit` `submit` action — non-admin can edit any congregation

- **Severity:** CRITICAL
- **File(s):** `src/routes/edit/+page.server.ts:167-296` (specifically lines 184-189)
- **Description:** The `submit` action only checks that the user is logged in:
  ```ts
  if (!client?.id) {
    const error = new Error('Forbidden') as ClientResponseError;
    error.status = 403;
    throw error;
  }
  ```
  There is **no check** that `client.congregation === data.id` for non-admins. A non-admin user can submit a form with any `data.id` and update any congregation's record (name, flavor, contact info, security settings, etc.). Compare with the `delete` action on lines 104-108, which correctly checks `!client?.admin && client?.congregation !== data.id`. The two actions are asymmetric.
- **Why it matters:** Any authenticated user can vandalize or hijack any other user's congregation listing. Given the political sensitivity of the directory (Jewish congregations welcoming to anti-war Jews), this is a high-impact attack.
- **Affected code path:** Logged-in non-admin user → `POST /edit?/submit` with `id` set to another user's congregation ID → update succeeds.
- **Root cause:** Missing authorization check, likely an oversight given that `delete` has it.
- **Recommended fix:** Mirror the `delete` action's check:
  ```ts
  if (!client?.admin && client?.congregation !== data.id) {
    const error = new Error('Forbidden') as ClientResponseError;
    error.status = 403;
    throw error;
  }
  ```
  Better: extract this into a shared `assertCanMutateCongregation(client, congregationId)` helper and use it in both `submit` and `delete`.
- **Verification:** E2E test where user A creates a congregation, user B signs up, then user B POSTs to `/edit?/submit` with user A's congregation ID — expect 403.

#### S-3. IDOR in `/user/lang` POST endpoint — any user can change any other user's language

- **Severity:** CRITICAL
- **File(s):** `src/routes/user/lang/+server.ts:8-34`
- **Description:**
  ```ts
  export async function POST({ cookies, locals, request }) {
    const { api, captureException } = locals;
    const client = api?.authStore?.record;
    const { lang, user } = await request.json();
    ...
    if (user) {
      result = await api.collection('users').update(user, { lang });
    }
  }
  ```
  `user` is taken from the request body. There is no check that `client.id === user`. Any authenticated user can change the `lang` field of any other user by posting `{"lang":"he","user":"<other-user-id>"}`.
- **Why it matters:** Privilege escalation primitive. While `lang` itself is low-impact, the same pattern can be reused if more fields are added. It also breaks i18n for victims (forcing Hebrew RTL, etc.). The endpoint is a `+server.ts` (raw JSON POST), so it does not get SvelteKit's automatic CSRF protection either — see S-4.
- **Affected code path:** Authenticated user A → `POST /user/lang` with `{"user":"<user-B-id>","lang":"he"}` → user B's `lang` is updated.
- **Root cause:** Missing `client.id === user` check.
- **Recommended fix:**
  ```ts
  if (user && user !== client?.id) {
    return json({ error: 'Forbidden' }, { status: 403 });
  }
  const targetUser = user ?? client?.id;
  if (!targetUser) {
    return json({ error: 'Unauthorized' }, { status: 401 });
  }
  result = await api.collection('users').update(targetUser, { lang });
  ```
  Also: validate `lang` against `['en','es','fr','he']` before writing.
- **Verification:** Unit test: authenticated client A POSTs with B's user ID → expect 403. POST with own ID → expect 201.

#### S-4. `+server.ts` endpoints lack CSRF protection

- **Severity:** HIGH
- **File(s):** `src/routes/user/lang/+server.ts:8`
- **Description:** SvelteKit form actions (`+page.server.ts` `actions`) get automatic CSRF protection via the `origin` check. Raw `+server.ts` POST endpoints do not. The `/user/lang` endpoint accepts a JSON POST from any origin (cookies are `sameSite: 'lax'`, which permits top-level cross-origin POSTs).
- **Why it matters:** A malicious site can `fetch('https://opencommunities.info/user/lang', { method:'POST', credentials:'include', body: JSON.stringify({lang:'he', user: victimId}) })` from a top-level navigation and trigger the IDOR above.
- **Affected code path:** Victim visits attacker site → attacker site top-level POSTs to `/user/lang` → victim's lang changes.
- **Root cause:** SvelteKit's CSRF protection is opt-in for `+server.ts`.
- **Recommended fix:** Either (a) convert to a form action, or (b) check `event.request.headers.get('origin')` against `env.PUBLIC_HOSTNAME` and reject mismatches.
- **Verification:** Test that a cross-origin POST (different Origin header) is rejected with 403.

#### S-5. PocketBase filter injection in multiple `getFirstListItem` calls

- **Severity:** CRITICAL (where reachable by unauthenticated users), HIGH (admin-only)
- **File(s):**
  - `src/routes/[slug]/+page.server.ts:10` — `getFirstListItem(\`slug="${params.slug}"\`)` — **unauthenticated**
  - `src/routes/edit/+page.server.ts:47` — `getFirstListItem(\`id="${id}"\`)` — admin-controlled `id`, but `id` comes from `url.searchParams`
  - `src/routes/edit/+page.server.ts:326` — `getFirstListItem(\`email="${data.email}"\`)` — form-validated email, but Zod's `z.email()` does not disallow `"` characters in all cases
  - `src/lib/location.ts:99` — `filter: \`country="${country?.id}"\`` — client-provided country ID
  - `src/lib/location.ts:144` — `filter: \`state="${state?.id}"\`` — client-provided state ID
  - `e2e/helpers/pb-helper.js:8` — `filter: \`email~"${prefix}"\`` — test helper, lower priority
- **Description:** PocketBase filter strings are constructed via template literal interpolation. If the interpolated value contains a `"` character or filter syntax (`'`, `&&`, `||`, `(`, `)`, comparison operators), the filter can be modified to return records the developer did not intend. The PocketBase JS SDK ships a `pb.filter(expr, params)` helper specifically for parameterized filters — it is never used in this codebase.
- **Why it matters:**
  - `/[slug]` is unauthenticated and queries the `pages` collection. An attacker can craft a slug like `nonexistent" || id != ""` to enumerate all page records (which may include draft/unpublished content).
  - `/edit` admin queries with `id` from URL params — if an attacker (or malicious admin) crafts `id="abc" || owner="<victim>"`, they can manipulate the query.
  - Even form-validated fields like email are at risk if the validator misses edge cases. Zod's `z.email()` is permissive about quoted local parts.
- **Affected code path:** `GET /<slug>` → `load` → `getFirstListItem(\`slug="${params.slug}"\`)` → PocketBase parses the injected filter.
- **Root cause:** Unfamiliarity with `pb.filter()` helper, or copy-paste from examples that don't show the parameterized form.
- **Recommended fix:** Use `pb.filter()` everywhere:
  ```ts
  // before
  await api.collection('pages').getFirstListItem(`slug="${params.slug}"`, { fetch })
  // after
  await api.collection('pages').getFirstListItem(pb.filter('slug = {:slug}', { slug: params.slug }), { fetch })
  ```
  Also add server-side validation that `params.slug` matches `^[a-z0-9-]+$` before querying.
- **Verification:** Test `GET /<slug>` with slug value `" || id != ""` — expect 404 or controlled error, not a 200 with leaked records. Add fuzz test that submits filter-injection strings in all `getFirstListItem` inputs.

#### S-6. Auth cookies are not `httpOnly`, not `secure`, and `sameSite: 'lax'`

- **Severity:** CRITICAL
- **File(s):** `src/hooks.server.ts:59-65`
- **Description:**
  ```ts
  event.locals.cookieOpts = {
    httpOnly: false,
    maxAge: 60 * 60 * 24 * 1, // 1 day
    path: '/',
    sameSite: 'lax'
    // secure: !dev
  } as SerializeOptions & { path: string };
  ```
  - `httpOnly: false` — the auth cookie (containing the PocketBase auth token) is readable by any client-side JavaScript. Combined with the CSP allowing `'unsafe-inline'` and `'unsafe-eval'` scripts (S-7), any XSS exfiltrates the auth token.
  - `secure: !dev` is commented out — cookies are sent over plaintext HTTP in production. The `dev` import is even commented out on line 11.
  - `sameSite: 'lax'` is OK for top-level navigations but permits cross-site POSTs on top-level navigation (relevant for S-4).
- **Why it matters:** Auth token theft via XSS, auth token interception via passive network observation, and CSRF amplification.
- **Affected code path:** Any XSS (e.g., via `@html` rendering of page content — S-8) → `document.cookie` returns the `auth` cookie → attacker exfiltrates → full session hijack.
- **Root cause:** Likely set to `httpOnly: false` to allow client-side PostHog identification, but the proper pattern is to expose a non-sensitive session ID to JS and keep the auth token server-side only.
- **Recommended fix:**
  ```ts
  import { dev } from '$app/environment';
  ...
  event.locals.cookieOpts = {
    httpOnly: true,
    maxAge: 60 * 60 * 24,
    path: '/',
    sameSite: 'strict',
    secure: !dev
  } as SerializeOptions & { path: string };
  ```
  Then either (a) read auth state from a `+layout.server.ts` and pass it down as `data.user` (already done — so the cookie being httpOnly is fine), or (b) introduce a separate non-sensitive `session` cookie for client-side identification (already attempted via the `session` cookie, but that's currently also non-httpOnly and unused for any server validation).
- **Verification:** Browser dev tools → Application → Cookies → `auth` cookie should have `HttpOnly` and `Secure` flags. Verify the app still works (login, logout, navigation) with httpOnly on.

#### S-7. CSP allows `'unsafe-eval'` and `'unsafe-inline'` in `script-src`

- **Severity:** CRITICAL
- **File(s):** `src/lib/server/security.ts:41-59`
- **Description:** The Content-Security-Policy's `script-src` includes `'unsafe-eval'` and `'unsafe-inline'`. `script-src-elem` and `style-src` also include `'unsafe-inline'`. These directives defeat the entire purpose of CSP — any injected script can run.
- **Why it matters:** CSP is the last line of defense against XSS. With `'unsafe-inline'`, an attacker who can inject `<script>…</script>` or `onerror=…` into the DOM executes arbitrary JS. Combined with `httpOnly: false` auth cookies (S-6), this is a complete XSS → session theft chain.
- **Affected code path:** Any HTML injection vector (e.g., `@html content.content` in `src/lib/components/form/form.svelte:198` — see S-8) → script executes under CSP → reads `document.cookie` → exfiltrates auth token.
- **Root cause:** Likely added to make a specific library work (MapLibre or PostHog may use eval), then never tightened.
- **Recommended fix:**
  1. Identify which library needs `unsafe-eval` (likely none in production) and remove it.
  2. Replace `'unsafe-inline'` with nonce-based CSP: generate a per-request nonce in `hooks.server.ts`, set it on the `<script>` tags via Svelte's `_render` mechanism, and add `'nonce-<value>'` to `script-src`. SvelteKit supports this via `resolve(event, { transformPageChunk })` injecting `<meta>` or via the `csp` option in `svelte.config.js`.
  3. For `style-src`, Tailwind generates scoped class names at build time, so `'unsafe-inline'` is unnecessary in production.
- **Verification:** Run the app with CSP reporting mode (`Content-Security-Policy-Report-Only`), exercise all features, confirm no reports. Then switch to enforcing. Check browser dev tools → Network → response headers → CSP header has no `'unsafe-eval'` or `'unsafe-inline'`.

#### S-8. `{@html content.content}` renders untrusted database HTML

- **Severity:** HIGH
- **File(s):** `src/lib/components/form/form.svelte:198`
- **Description:**
  ```svelte
  {#if mode === 'add' && content && !$appState.form?.success}
    <div class="prose w-full">{@html content.content}</div>
  {/if}
  ```
  `content` is a `PagesRecord` from the `pages` collection. `content.content` is typed as `HTMLString`. The ESLint rule `svelte/no-at-html-tags` is disabled in `eslint.config.js:104` for `.svelte` files, so this goes unflagged. If any path exists for non-admins to write to the `pages` collection (current admin-only path means this is only exploitable by compromised admins, but PocketBase API rules may not actually enforce admin-only — that depends on the schema which I couldn't fully verify), it's XSS. Also renders in emails indirectly via the `marked` pipeline (S-9).
- **Why it matters:** Stored XSS in the form page. Even if admin-only today, the trust boundary shrinks if any admin account is phished or if a future feature lets non-admins edit pages.
- **Affected code path:** PocketBase `pages.content` field → `load` → `data.content` → `{@html}` → DOM.
- **Root cause:** `svelte/no-at-html-tags` rule disabled; no sanitization layer.
- **Recommended fix:**
  1. Re-enable `svelte/no-at-html-tags` in `eslint.config.js`.
  2. Sanitize before rendering: `DOMPurify.sanitize(content.content)` (add `isomorphic-dompurify` for SSR).
  3. Better: store page content as Markdown and render with `marked` + `DOMPurify`, not raw HTML.
- **Verification:** Insert `<script>alert(1)</script>` into a page's `content` field via PocketBase admin UI → load the page → no alert. Re-enable lint rule → `pnpm lint` flags any remaining `{@html}`.

#### S-9. Email HTML injection via `marked.parseInline` + `String.replace`

- **Severity:** HIGH
- **File(s):** `src/lib/server/mail.ts:50`
- **Description:**
  ```ts
  const html = emailTemplate?.replace('%MESSAGE%', `${await marked.parseInline(message)}`);
  ```
  `message` is user-controlled (from contact form, add form, edit form). `marked.parseInline` does NOT sanitize HTML — it returns HTML with user-supplied tags intact. So if `message` is `<img src=x onerror=alert(1)>`, the resulting email HTML contains that tag verbatim. While email clients don't execute `<script>`, they do execute event handlers in some clients (Outlook, older Apple Mail). At minimum, this enables:
  - Phishing: attacker injects `<a href="https://evil.com">Click to verify</a>` into a "transactional" email the victim trusts.
  - Tracking pixels: `<img src="https://attacker.com/pixel.png">` confirms the victim's email is active.
  - Layout disruption: `<table>`, `<style>` injection breaks email rendering.
- **Why it matters:** The transactional email is sent from `no-reply@m.opencommunities.info` — recipients trust it. HTML injection turns that trust into a phishing vector.
- **Affected code path:** User submits `message: '<a href="https://evil.com">Verify your account</a>'` via `/contact` → `adminMail()` → `marked.parseInline()` preserves the `<a>` tag → email sent to admin (or to the user, in `transactionalMail`).
- **Root cause:** `marked` is Markdown, not HTML-safe. The output is interpolated into an HTML template via `String.replace`, which doesn't escape.
- **Recommended fix:**
  ```ts
  import DOMPurify from 'isomorphic-dompurify';
  ...
  const messageHtml = await marked.parseInline(message);
  const sanitized = DOMPurify.sanitize(messageHtml, { ALLOWED_TAGS: ['a','b','i','em','strong','br','p'], ALLOWED_ATTR: ['href'] });
  const html = emailTemplate?.replace('%MESSAGE%', sanitized);
  ```
  Also escape the message for the `text` part: `text = message` (line 51) is fine since it's plain text, but ensure no CRLF injection (see S-10).
- **Verification:** Submit contact form with `message: '<script>alert(1)</script><a href="https://evil.com">phish</a>'` → check Mailpit → email HTML should contain escaped or stripped tags, no `<script>`.

#### S-10. Email header injection via user-controlled `from`/`name`/`email`

- **Severity:** HIGH
- **File(s):** `src/lib/server/mail.ts:35`, `src/lib/server/mail.ts:45-58`, callers in `src/routes/add/+page.server.ts:138-149`, `src/routes/edit/+page.server.ts:249-260`, `src/routes/contact/+page.server.ts:71-84`
- **Description:** `mailTransport` builds the `from` header from user input:
  ```ts
  await mailTransport({
    from: `${name} via Open Communities <${email}>`,
    ...
  });
  ```
  If `name` or `email` contains a newline (`\r\n`), nodemailer will interpret the bytes after the newline as new SMTP headers. An attacker can inject `Bcc: victim@example.com` to send copies to arbitrary addresses, or inject a completely new email body. The schemas (`contactSchema`, `userSchema`) validate email format with `z.email()` but **do not reject newlines**, and `name` is just `z.string()`.
- **Why it matters:** Email header injection is a classic vulnerability that turns a contact form into a spam relay. The app's IP/domain reputation suffers, and victims of injected BCCs may report the domain as malicious.
- **Affected code path:** Attacker → `/contact` with `name: "abc\r\nBcc: victim@evil.com"` → `adminMail` → `mailTransport` → `from: "abc\r\nBcc: victim@evil.com via Open Communities <...>"` → SMTP server parses Bcc.
- **Root cause:** No sanitization of header-bound user input.
- **Recommended fix:**
  ```ts
  function sanitizeHeader(value: string): string {
    return value.replace(/[\r\n]/g, ' ').trim();
  }
  ...
  from: `${sanitizeHeader(name)} via Open Communities <${sanitizeHeader(email)}>`,
  ```
  Also tighten schemas: `name: z.string().regex(/^[^\r\n<>]+$/).max(200)`.
- **Verification:** Submit contact form with `name: "abc\r\nBcc: test@evil.com"` → check Mailpit raw email → only one `From` header, no `Bcc`.

#### S-11. SMTP transport disables TLS certificate verification

- **Severity:** CRITICAL
- **File(s):** `src/lib/server/mail.ts:62-66`
- **Description:**
  ```ts
  const transportOpts = {
    host: SMTP_HOST as string,
    port: parseInt(SMTP_PORT as string, 10),
    secure: false,
    tls: { rejectUnauthorized: false }
  } as unknown as nodemailer.TransportOptions;
  ```

#### P-11. Module-level PocketBase singleton mutated per-request

- **Severity:** CRITICAL (concurrency)
- **File(s):** `src/lib/server/api.ts:17`, `src/hooks.server.ts:38-47`
- **Description:**
  ```ts
  // api.ts
  const api = new PocketBase(env.PUBLIC_API_ENDPOINT) as TypedPocketBase;
  ...
  // hooks.server.ts
  event.locals.api = api;
  event.locals.api.beforeSend = function (url, options) {
    options.headers = assign({}, { ...options.headers, 'X-PocketHost-Client-Ip': clientIp });
    return { options, url };
  };
  ```
  `api` is a singleton shared across all requests. `event.locals.api.beforeSend = ...` mutates the singleton. Under concurrent requests, request A's `beforeSend` (with clientIp A) is overwritten by request B's `beforeSend` (with clientIp B) before request A's PB call fires. So PocketBase records the wrong client IP for ~50% of requests under load.
- **Why it matters:** Audit log integrity (related to S-15, S-18). Also: if any future code stores per-request state on `api`, it leaks between requests.
- **Recommended fix:** Create a new PocketBase instance per request, OR use AsyncLocalStorage to bind the client IP to the request context and have `beforeSend` read from there.
  ```ts
  import { AsyncLocalStorage } from 'node:async_hooks';
  const requestContext = new AsyncLocalStorage<{ clientIp: string }>();
  
  // in hooks.server.ts
  await requestContext.run({ clientIp }, async () => {
    event.locals.api = api; // shared, but beforeSend reads from ALS
    return resolve(event);
  });
  
  // in api.ts at module load
  api.beforeSend = (url, options) => {
    const ctx = requestContext.getStore();
    if (ctx) {
      options.headers = { ...options.headers, 'X-PocketHost-Client-Ip': ctx.clientIp };
    }
    return { options, url };
  };
  ```
- **Verification:** Load test with 100 concurrent requests from different IPs → PocketBase audit log should show correct IP for each request, not cross-contamination.

## Final Recommendation

**BLOCK UNTIL FIXED.**

The codebase has good bones — modern Svelte 5, typed PocketBase, comprehensive test files (when they run), reasonable structure. But the current state has multiple CRITICAL security defects that are exploitable by unauthenticated or low-privilege attackers:

1. Captcha bypass (S-1) — every form is open to abuse.
2. IDOR in `/edit` submit (S-2) — any user can vandalize any congregation.
3. IDOR in `/user/lang` (S-3) — any user can tamper with any other user.
4. PocketBase filter injection on unauthenticated routes (S-5).
5. Hardcoded secrets in CI (S-12).
6. Insecure auth cookies (S-6) + permissive CSP (S-7) — XSS chain to session theft.
7. SMTP TLS disabled (S-11) — email credential interception.
8. Concurrency bug (P-11, D-2) — auth state corruption under load.

Additionally, the **entire unit test suite does not run** due to a library incompatibility (T-1 test), and CI tolerates this via `continue-on-error: true`. This means no regression protection exists. Any fix could break anything without detection.

**Recommended path forward:**

2. **This week:** Phase 2 (Steps 2.1–2.10). Re-enable lint, fix type safety, fix performance bottlenecks, fix test suite, remove `continue-on-error`.
3. **This month:** Phase 3 (Steps 3.1–3.12). Architectural cleanup, security headers, documentation.
4. **Ongoing:** Phase 4. Polish.

After Phase 1, the app is reasonably safe to deploy. After Phase 2, it's maintainable. After Phase 3, it's a model SvelteKit app. Phase 4 is gravy.
